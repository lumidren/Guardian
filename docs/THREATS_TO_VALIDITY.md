# Threats to Validity

This document provides a rigorous methodological assessment of threats to validity for the GUARDIAN evaluation framework, structured according to established empirical software engineering and cybersecurity evaluation standards.

---

## 1. Internal Validity

Internal validity examines whether the experimental setup correctly establishes causal relationships without confounding factors or systematic bias.

### 1.1 Temporal Data Leakage and Split Hygiene
- **Risk**: In network anomaly detection, random cross-validation leaking future traffic patterns into historical training baselines artificially inflates detection accuracy.
- **Mitigation**: GUARDIAN strictly enforces time-ordered sequential splits across a 14-day timeline:
  - **Days 1–7 (Train)**: Benign baseline profiling and model training.
  - **Day 8 (Calibration)**: Threshold selection and operating point freezing.
  - **Days 9–14 (Test)**: Ground-truth attack episodes mixed into unseen normal traffic.
  Models are never retrained on or exposed to calibration or test split data during evaluation.

### 1.2 Attack Traffic Realism and Background Noise
- **Risk**: Early evaluation prototypes (Audit Finding **F5**) evaluated attacks in isolation without background normal traffic, artificially exaggerating feature deviations.
- **Mitigation**: The `ScenarioBuilder` injects attack packets directly into ongoing, live normal background streams generated by the `IoTFleetEmulator`. Every attack window contains real background packets with natural jitter.

### 1.3 Uniform Operating Point
- **Risk**: Using disparate score thresholds for True Positive Rate (TPR) and False Positive Rate (FPR) (Audit Finding **F6**) biases reported performance.
- **Mitigation**: A single `OperatingPoint` is calibrated on the clean Day 8 split to meet an explicit target false positive rate ($FPR \le 0.05$) and frozen. The exact same decision threshold governs both TPR and FPR during testing.

## 2. External Validity

External validity evaluates the extent to which evaluation findings generalize to real-world operational environments.

### 2.1 Simulation vs. Physical Hardware Testbeds
- **Constraint**: Phase 2 explicitly operates within a software-based discrete event emulator without requiring dedicated physical Raspberry Pi 4 or hardware router appliances.
- **Threat**: Synthetic packet arrival times generated via statistical distributions (e.g. Poisson, circadian sinusoids) do not capture physical hardware artifacts such as packet buffer drops, Linux network stack interrupt coalescing, CPU thermal throttling, or Wi-Fi radio interference.
- **Mitigation**: While empirical metrics are measured on real Python processes using OS-level counters (`psutil`, monotonic `time.perf_counter`), reports explicitly declare these as software-emulated measurements rather than embedded hardware measurements (Audit Finding **F10**).

### 2.2 Device Profile Diversity
- **Threat**: The fleet comprises 8 standard IoT device specifications (sensors, cameras, smart plugs, environmental monitors). Enterprise environments with thousands of heterogeneous embedded devices may introduce higher variance.
- **Mitigation**: Devices span three distinct communication archetypes:
  - Low-frequency sensor telemetry (MQTT, CoAP).
  - High-bandwidth multimedia streaming (RTSP, HTTPS).
  - Bursty intermittent control (HTTP, REST APIs).

### 2.3 Adversarial Evasion Realism
- **Threat**: Attackers in production actively attempt evasion rather than executing naive script-kiddie volumetric floods.
- **Mitigation**: Evaluated against four systematic evasion tactics (`EvasionMode`):
  1. **Mimicry**: Adversary matches packet length distributions and inter-arrival timing to legitimate traffic.
  2. **Low-and-Slow**: Transmits at 15% rate volume over extended durations to evade rate tripwires.
  3. **Delayed Start**: Implants remain dormant before firing payload packets.
  4. **No-New-Destination**: Restricts all attack traffic strictly to authorized network destinations.

## 3. Construct Validity

Construct validity concerns whether the mathematical metrics accurately reflect the operational phenomena being evaluated.

### 3.1 Window-Level FPR vs. Operational Alert Fatigue
- **Threat**: Reporting window-level FPR (e.g. 1%) obscures operational realities: on 10-second windows (8,640 windows/device/day), a 1% FPR produces ~86 false alerts per device per day, overwhelming SOC teams.
- **Mitigation**: In addition to classical confusion matrix rates ($TPR, FPR$), GUARDIAN reports **False Alerts Per Device Per Day** with **hysteresis**:
  $$\text{FAR} = \frac{\text{Total False Alert Incidents}}{\text{Device Count} \times \text{Days Observed}}$$
  Consecutive alerting windows are treated as a single incident rather than independent false alarms.

### 3.2 Time-to-Detect and Operational Deadlines
- **Threat**: An attack detected after 30 minutes may still count as a "true positive" in naive benchmarks, despite catastrophic system compromise having already occurred.
- **Mitigation**: Episodes are subject to a strict **60-second detection deadline**. Any detection occurring after 60 seconds is scored as a false negative ($FN$). Compute latency, time-to-detect from attack onset, and firewall enforcement latency are measured independently.

## 4. Reliability and Reproducibility

Reliability ensures that independent researchers can replicate identical experimental results.

### 4.1 Determinism and Seed Control
- All pseudo-random number generation utilizes deterministic numpy PRNG generators (`np.random.default_rng(seed)`).
- Identical seeds produce bit-for-bit identical packet schedules, feature vectors, and evaluation metrics.

### 4.2 Cryptographic Artifact Caching
- Models are cached with SHA-256 content hashes of training data, feature registries, and configurations.
- Model sidecars verify cryptographic signatures on load, immediately rejecting tampered or corrupted bundles (`TamperedBundleError`, Audit Finding **F9**).
- Missing model checkpoints raise `ArtifactMissingError` immediately rather than silently returning default zero scores (Audit Finding **F8**).
